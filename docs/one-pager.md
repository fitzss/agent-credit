# Agent Tab — VC One-Pager

## What is Agent Tab?
Agent Tab is a **control, obligation, and settlement layer for agent workflows**.

The core idea is simple: **agents can already do useful work across many paid tools, but the commercial rails around them are still built for human checkout** — prepaid balances, fragmented billing, approval loops, cards on file, and rigid settlement.

Agent Tab is meant to fill that gap.

## The problem
Today, AI agents can:
- call models
- browse
- search
- use APIs
- orchestrate multi-step workflows

But once they start consuming paid services across multiple providers, the workflow often breaks on:
- prepaid balances
- scattered billing relationships
- manual approval loops
- hard quotas
- no clear delegated authority
- no clean way to represent what the agent has obligated a company to pay

So the bottleneck is no longer just model capability.

**The bottleneck is commercial coordination.**

## The missing primitive
The market lacks a clean way for software to:
- act under authority
- use paid services under clear limits
- create bounded obligations
- continue the workflow
- settle later without forcing every action through checkout

That is why this is not just "payments for agents."

The deeper idea is:

**bounded commercial agency for software**

Or more plainly:

**turn software capability into economically usable agency.**

## What the product does
The first product wedge is a **control and obligation layer** for teams whose agents already break on billing and authority friction.

In practice, that means:
- this agent
- these tools
- this cap
- this expiry
- this approval threshold
- this running obligation / exposure

So a company can let trusted agents keep working **without losing control**.

## What has been built
Today, Agent Tab is not just a concept. It is a real early **settlement substrate**.

Current system components:
- **Agent Tab** as the off-chain commercial layer
- **Sidecar** for proof generation / transaction construction
- **Basis reserve** as the on-chain settlement backstop

Current capabilities proven in the prototype include:
- off-chain cumulative obligations
- reserve-backed settlement
- one-shot redemption
- repeated same-pair redemption
- multi-pair tracker state
- debt transfer / novation
- recovery / realignment logic

The honest framing is:

**strong v0.1 settlement substrate, not yet a full market network.**

## The go-to-market wedge
The first wedge is **not** asking every provider to adopt a new credit network.

The better first step is:
- help teams manage agent spend and authority across multiple paid tools
- record what agents obligate the company to pay
- keep providers mostly unchanged early on
- grow into the deeper settlement / network model over time

So the sequence is:

**control layer first → broader obligation layer → deeper network / settlement adoption later**

## Why this could get very big
If agents become meaningful economic actors, the world will need more than API calls and billing dashboards.

It will need infrastructure that defines:
- what software is allowed to do commercially
- what software is allowed to owe
- what limits apply
- how obligations accumulate
- how providers get recourse
- how settlement happens without killing usability

That is the larger opportunity:

**the commercial operating layer for software labor**
