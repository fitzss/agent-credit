# Dedicated Demo Reserve (slice 13b)

`agent-tab/scripts/seed-settlement-demo-reserve.ts`

A phased CLI tool that prepares a **second reserve under Demo Debtor** so that
slice 13c can demonstrate end-to-end receipt-to-reserve settlement without ever
touching the canonical reserve `e7f6f1c2`. The canonical reserve must remain
stable for `prove.sh`'s settlement-substrate suite.

## Why this reserve exists

The whitepaper thesis is `work → Work Receipt → obligation → settlement`. Slice
12a.1 shipped Work Receipts. Slice 13a shipped the read-only readiness audit.
Slice 13c will demonstrate end-to-end receipt-to-reserve settlement.

Before 13c can run, we need a reserve we can settle against without breaking
prove.sh's settlement-substrate suite (12/12), which depends on the canonical
reserve's specific state. This script creates an isolated demo reserve under
Demo Debtor that 13c will use exclusively. The canonical reserve is never
touched.

## Prerequisites

- Testnet wallet with **≥ 0.6 ERG** free (deploy collateral defaults to 0.5 ERG
  plus tx fees).
- Sidecar running (`http://localhost:8081`).
- Ergo node running (`http://localhost:9052`), wallet unlocked.
- Demo Debtor customer (id `86c0dc8d-506b-41d8-af24-27abe58499f7`) exists in
  the DB. (Already present in any working dev DB.)
- Demo Debtor's owner secret file already on disk at
  `~/.chaincash-secrets/owner-031b951d.json`. (Created on first canonical
  redeem; reused by 13c.)

## Phased CLI

The script runs in four mutually exclusive phases that map to the lifecycle of
a real on-chain reserve:

```
Phase 1: --prepare    register Reserve row + save deploy spec to disk
Phase 2: (operator)   submit deploy tx via Ergo wallet (out of script scope)
Phase 3: --sync       scan from chain; transition lifecycle requested → active
Phase 4: --status     read-only inspection at any time
Phase 5: --cleanup    mark depleted, delete demo-state files
```

Exit codes are the same across phases:

| Code | Meaning |
|---|---|
| `0` | success / idempotent no-op |
| `1` | recoverable failure (sidecar down, chain not yet visible, manifest references missing row, etc.) |
| `2` | misuse / canonical-ID collision / corrupt manifest / customer mismatch |

## Phase 1: `--prepare`

Validates inputs, calls the sidecar's `deployReserve` directly to get the
on-chain deploy spec, registers the Reserve row at `lifecycle=requested`, and
saves the spec to disk for the operator to submit. (The script bypasses
`POST /api/reserves` to avoid a known BigInt serialization bug in that route's
201 response and to keep the create path script-local.)

```bash
npx tsx agent-tab/scripts/seed-settlement-demo-reserve.ts --prepare \
  --tracker-nft-id <hex64> \
  --reserve-token-id <hex64> \
  --initial-collateral-erg 0.5
```

Both `--tracker-nft-id` and `--reserve-token-id` are 64-char lowercase hex
values for tokens you have already minted on testnet (see "Minting the tokens"
below). `--initial-collateral-erg` is optional; default 0.5, range 0.1–10.

### What it writes

- **Reserve row** in the DB at `lifecycle=requested`. UUID id auto-generated by
  Prisma.
- **`agent-tab/.demo-state/settlement-demo-reserve.json`** — the manifest
  (operator-readable record of what was prepared).
- **`agent-tab/.demo-state/settlement-demo-reserve-deploy.json`** — the deploy
  spec, mode `0o600`. Contains the `deploymentRequestJson` you submit via your
  wallet plus `reserveAddress` and `network`.

Both files are gitignored at `agent-tab/.gitignore` (`.demo-state/`).

### Defensive guards before any side effect

- Refuses with exit 2 if `--reserve-token-id` matches the canonical reserve
  token (`2b700ca1...`).
- Refuses with exit 2 if `--tracker-nft-id` matches the canonical tracker NFT
  (`d234898d...`).
- Refuses with exit 2 if a manifest already exists pointing at a different
  `reserveTokenId` than the one passed.
- Refuses with exit 2 if no manifest but a Reserve row already exists for the
  given tokenId — see "Recovery: orphan row" below.

### Secret-key scanner

After `POST /api/reserves` returns, the script recursively scans the
`deployment` object for any object key matching
`/secret|private|seed|mnemonic|password/i`. If any match is found, the script
**refuses to persist the deploy spec** and exits 1 with the offending key
NAME (never the value). This is a defensive guard; the sidecar is not expected
to return any such field.

## Phase 2: operator submits the deploy tx (manual)

The script does NOT submit the deploy tx for you. After `--prepare`, open the
saved deploy spec and submit it via your Ergo wallet:

```bash
DEPLOY_SPEC=$(jq -c '.deploymentRequestJson' agent-tab/.demo-state/settlement-demo-reserve-deploy.json)
curl -s -X POST http://localhost:9052/wallet/transaction/send \
  -H "api_key: hello" \
  -H "Content-Type: application/json" \
  -d "$DEPLOY_SPEC"
```

The exact wallet API path may differ depending on your Ergo node configuration.
The default for this project (per `CLAUDE.md`) uses `api_key: hello` and the
wallet must be unlocked with the same password.

Alternatively, the sidecar's `POST /reserve/build-and-submit` endpoint will
sign and submit in one call against the configured wallet — useful when the
wallet API path is not what the doc above assumes.

After submission, **wait for at least one block** (typically ~2 minutes on
testnet). You can confirm the transaction landed by querying the node:

```bash
TX_ID=<txId from the wallet response>
curl -s http://localhost:9052/blockchain/transaction/byId/$TX_ID | jq .id
```

If the tx is in the mempool but not yet confirmed, the response will indicate
that; re-poll every few seconds.

For canonical-reserve setup history and persistence semantics, see
`docs/fixture-reuse-note.md`.

### Minting the tokens

The precise minting commands for the tracker NFT and reserve token are not in
this codebase — they're an operator-driven Ergo wallet operation. Each token is
minted as part of an issuance transaction (the wallet creates the token id from
the boxId of one of the inputs). Refer to the Ergo wallet API documentation
and to your testnet wallet's interface. Once each token's tx has confirmed,
copy the resulting 64-char hex token id and pass it as `--reserve-token-id` or
`--tracker-nft-id` to `--prepare`.

## Phase 3: `--sync`

Once the deploy tx has confirmed, run:

```bash
npx tsx agent-tab/scripts/seed-settlement-demo-reserve.ts --sync
```

`--sync` calls `PATCH /api/reserves` (the existing scan-from-chain route) which
queries the sidecar's `/reserve/status?reserveTokenId=...` and, if the reserve
is found on-chain, transitions the DB row to `lifecycle=active` with `boxId`,
`valueNanoErg`, `avlTreeDigest`, and `creationHeight` populated.

### Resumable failure path

If the chain has not yet confirmed the deploy tx, the script exits 1 with:

```
Reserve not yet visible on-chain. Wait for testnet confirmation
(typically 1-2 blocks) and re-run --sync. Manifest preserved; DB row
remains at lifecycle=requested. Resumable.
```

Re-run `--sync` after a short wait. The route is idempotent.

### When `--sync` succeeds

The DB row is at `lifecycle=active`, the manifest's `syncedAt` is set, and the
script prints the next-step verification command:

```
npx tsx scripts/check-settlement-readiness.ts \
  --reserve-id <uuid> \
  --latest-repo-lint
```

Expected: `summary.result: "FAIL"` with blockers naming `tracker-entry-missing`
and possibly `receiver-secret-missing`. **This is the useful FAIL** — exactly
what 13c will resolve. The fact that 13a's audit reports it correctly is the
proof that 13b's reserve and 13a's audit are wired together.

## Phase 4: verify with the 13a audit

Read `reserveId` from the manifest (or use `--status`) and run the audit:

```bash
RESERVE_ID=$(jq -r .reserveId agent-tab/.demo-state/settlement-demo-reserve.json)
npx tsx agent-tab/scripts/check-settlement-readiness.ts \
  --reserve-id "$RESERVE_ID" \
  --latest-repo-lint
```

Expected JSON output (truncated):

```json
{
  "summary": { "result": "FAIL", "checksTotal": 19, "checksFailed": 1, ... },
  "blockingReasons": [
    "[#13] TrackerEntry exists for pair: current TrackerBox has no entry for ..."
  ],
  "nextStep": "Audit FAIL. Resolve blocker(s): [#13] TrackerEntry exists for pair. Re-run audit."
}
```

The 13a audit will pass once 13c deploys a tracker entry for the
(Demo Debtor, mcp-demo-repo-tools-001) pair against this reserve.

## `--status` (read-only)

Use anytime to inspect manifest + DB + sidecar + deploy-spec state without
mutating anything.

```bash
npx tsx agent-tab/scripts/seed-settlement-demo-reserve.ts --status
npx tsx agent-tab/scripts/seed-settlement-demo-reserve.ts --status --json
```

Output shape (top-level keys):

```ts
{
  manifest: { reserveId, reserveTokenId, trackerNftId, customerId,
              preparedAt, syncedAt, deploySpecPath },
  db: { id, lifecycle, boxId, valueNanoErg, contractVersion,
        reserveAddress, avlTreeDigest, ... } | null,
  sidecar: { reachable, reserveStatus | null, error | null },
  deploySpec: { fileExists, filePath, reserveAddress, network, writtenAt },
  alignment: { dbAndSidecarBoxIdMatch, dbAndSidecarValueMatch,
               dbAndSidecarDigestMatch },
  hint: string
}
```

The full `deploymentRequestJson` is **not** in `--status` output — it lives in
the deploy-spec file on disk. `--status` only reports its presence and a small
metadata header.

## `--cleanup`

Two forms: manifest-tracked, and orphan-row-by-token.

### `--cleanup` (no flag) — manifest path

```bash
npx tsx agent-tab/scripts/seed-settlement-demo-reserve.ts --cleanup
```

- Reads the manifest, resolves the Reserve row by id.
- Refuses if any `PendingRedemption` exists for this reserve (run
  `/api/reserves/recover-pending` first).
- Refuses if any `SettlementEvent` with `redemptionTxId` references an
  obligation under Demo Debtor with this reserve's debtorPubKey (defensive —
  does not trigger in 13b).
- Refuses if the resolved row's `customerId` is anything other than Demo Debtor
  (defensive).
- Refuses if the resolved row's id matches the canonical reserve.
- Marks the row `lifecycle="depleted"` and `valueNanoErg=0`. Does NOT delete
  the row (preserves audit trail).
- Deletes both `agent-tab/.demo-state/settlement-demo-reserve.json` and
  `agent-tab/.demo-state/settlement-demo-reserve-deploy.json`.
- Does NOT sweep the on-chain UTXO box. That's the operator's responsibility,
  out of scope for this slice.

### `--cleanup --reserve-token-id <hex64>` — orphan-row path

For the case where `--prepare` POST succeeded but the secret-scanner refused
(or the operator manually deleted the manifest):

```bash
npx tsx agent-tab/scripts/seed-settlement-demo-reserve.ts --cleanup \
  --reserve-token-id <hex64>
```

- Validates hex format.
- Refuses with exit 2 if the tokenId matches the canonical reserve token.
- Looks up the Reserve by `reserveTokenId` (unique).
- Refuses if the row's `customerId` is not Demo Debtor.
- Refuses if the row's id matches the canonical reserve.
- Refuses if any PendingRedemption / SettlementEvent guard triggers (same as
  manifest path).
- Marks the row depleted. Deletes the manifest if it points at the same row.
  Best-effort: also deletes the deploy-spec file if its embedded
  `reserveAddress` matches.

## Recovery scenarios

### Manifest missing, DB row exists

Either secret-scanner refused after POST, or the operator deleted the manifest.
The Reserve row is real. **The script will NOT silently regenerate the manifest** — that would mask the prior failure. Run:

```bash
npx tsx agent-tab/scripts/seed-settlement-demo-reserve.ts --cleanup \
  --reserve-token-id <X>
```

Then re-run `--prepare`.

### Manifest exists, DB row missing

The DB was reset or the row was deleted out-of-band. The script exits 1 with
exact recovery commands:

```bash
rm agent-tab/.demo-state/settlement-demo-reserve.json
rm -f agent-tab/.demo-state/settlement-demo-reserve-deploy.json
# then re-run --prepare
```

### Manifest exists, DB row at lifecycle=requested, deploy-spec file MISSING

Operator-deleted spec file, or never persisted. **Re-run `--prepare`** with the
same args. The script detects this state and regenerates the deploy spec via a
direct sidecar call (`deployReserve()`). No new Reserve row is created; the
manifest is preserved (with `regeneratedAt` added to the spec file). Submit the
regenerated spec via your wallet.

### Mismatched tokenId in manifest

If the manifest exists with a different `reserveTokenId` than the one passed to
`--prepare`, the script refuses with exit 2. Either pass the correct tokenId or
run `--cleanup` first.

## Defensive guards (summary)

The script enforces these invariants BEFORE any side effect:

| Guard | Refuses if... | Exit |
|---|---|---|
| Canonical reserveTokenId | `--reserve-token-id == 2b700ca1...` (canonical) | 2 |
| Canonical trackerNftId | `--tracker-nft-id == d234898d...` (canonical) | 2 |
| Canonical Reserve.id | resolved row id == `e7f6f1c2-...` | 2 |
| Customer mismatch | resolved row's customerId != Demo Debtor | 2 |
| Hex format | tokenIds not 64-char lowercase hex | 2 |
| Collateral bounds | `--initial-collateral-erg` < 0.1 or > 10 | 2 |
| Pending redemption | any PendingRedemption row references this reserve | 1 |
| Settlement history | SettlementEvent (with redemptionTxId) under same debtor pubkey | 1 |
| Mismatched manifest | manifest pinned to different tokenId | 2 |
| Orphan detection | DB row exists, no manifest | 2 (--prepare) |
| Manifest references missing row | manifest exists, row absent | 1 |

## What 13b leaves ready for 13c

- A second `Reserve` row under Demo Debtor: `lifecycle="active"`, `boxId`
  populated, `valueNanoErg > 0`, on a real testnet UTXO under Demo Debtor's key.
  UUID id, resolvable via the manifest.
- Demo Debtor's owner secret file already on disk (reused).
- 13a audit reports a clear FAIL with `tracker-entry-missing` — proves the new
  reserve and 13a's audit are wired correctly.
- 13c's job becomes: charge a `mcp-demo-repo-tools-001` obligation, deploy a
  tracker entry for the (Demo Debtor, mcp-demo-repo-tools-001) pair against
  this reserve, run audit (expect PASS), call `/api/reserves/redeem`, record
  `SettlementEvent`. Canonical reserve untouched.

## What this script does NOT do

- Does not deploy a reserve box on-chain (operator's job).
- Does not mint `trackerNftId` or `reserveTokenId` (operator's job).
- Does not call `/api/reserves/redeem` or perform settlement.
- Does not write `SettlementEvent` or `PendingRedemption` rows.
- Does not mutate the canonical reserve.
- Does not change Prisma schema.
- Does not modify `chaincash/`, `reconcile.ts`, the redeem route, the sidecar
  client, `validate.sh`, or `prove.sh`.
- Does not generate any new private keys.
- Does not rewrite a DB primary key.
- Does not sweep the on-chain UTXO box during `--cleanup`.

## Connection to slice 13c

When 13c is implemented, it will:

1. Charge an obligation against `mcp-demo-repo-tools-001` (already shipped in
   12a.1) under Demo Debtor.
2. Deploy a tracker entry for the (Demo Debtor, repo-lint provider) pair on
   the demo reserve's tracker NFT.
3. Run the 13a audit — expect PASS.
4. Call `POST /api/reserves/redeem` with the demo reserve and the obligation.
5. Verify a `SettlementEvent` is created and the obligation is settled.
6. Confirm `prove.sh` is still 49/49 (will require `validate.sh`'s reserve
   discovery to keep picking the canonical reserve — handled in 13c, not
   13b).

## Why a phased CLI (instead of one big seed)

Each phase is one clear lifecycle step. The phases let the operator stop
between "registered in DB" and "submitted to chain" — a real, valuable boundary
that an all-in-one script would smear. The lifecycle states (`requested`,
`active`, `depleted`) are visible at the CLI surface; nothing is "active" in
the script's print output until the chain has confirmed.
